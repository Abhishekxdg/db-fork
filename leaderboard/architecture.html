Technical Architecture: Local & Cloud Setup

How BranchBench isolates benchmark execution, validates reproducibility, and assembles both local developer previews (local phase) and official cloud VM rankings (prod phase).

1. Architectural Boundary & Benchmark Suites

The leaderboard/ package is a self-contained harness and static site builder layered over dblib/, microbench/, and macrobench/ without modifying upstream files.

Open-Closed Boundary
All runner orchestration, system lifecycle hooks, connector shims, and UI assets live strictly inside leaderboard/. Automated boundary tests verify that zero files outside leaderboard/ differ from origin/main.
Macrobench (Agent workflows)
Six end-to-end stateful AI agent scenarios (rl_env, context_mgmt, multi_agent, dev_agent, ops_agent, data_agent) exercising nine Git-like branching verbs (branch, commit, diff, log, merge, rebase, revert, reset, delete) alongside concurrent SQL reads and writes. Ranked by one workflow's completion time at a time among verified attempts.
Microbench (Operations)
Eight isolated operations (time_to_first_query, branch_create, branch_connect, read, range_read, insert, update, range_update) plus initial load_time and provision_time on a deterministic CH-benCHmark seed (leaderboard/suite.json). Ranked by shifted geometric mean of ratios against the fastest comparable system.

2. Local Developer Setup (LEADERBOARD_PHASE=local)

Designed for database developers building and verifying a connector on their own workstation before opening a pull request.

CLI & HTTP Runner
python -m leaderboard.run <system> --machine <id> runs the microbench suite; python -m leaderboard.run_macro <system> --preset {mini|full} --machine <id> runs all six agent workflows in isolated subprocesses. python -m leaderboard.serve --phase local serves the site on port 8000 and exposes POST /api/run on loopback (127.0.0.1 / ::1), rejecting non-loopback or cross-origin requests with HTTP 403.
Single-Run Lock (run.lock)
Both runners acquire an exclusive non-blocking file lock at leaderboard/.runs/run.lock. Only one database benchmark can execute at a time on a machine so engines never contend for CPU cores, memory bandwidth, disk I/O, or local ports.
Crash Recovery (active.json)
Before starting a self-hosted server, the runner records the active system in leaderboard/.runs/active.json. If a process is killed (such as SIGKILL or power loss), the next invocation reads active.json and executes that system's stop script before starting a new run.
Local Site Assembly
python -m leaderboard.site --phase local scans leaderboard/*/results/ and leaderboard/*/macro/, validates every record against leaderboard/suite.json, pairs local runs with leaderboard.mock reference rows, and atomically swaps a staging directory into leaderboard/.site/local/.

3. Cloud Official Setup (LEADERBOARD_PHASE=prod & 1 DB = 1 VM)

Official rankings never ingest timing JSON files from developer laptops. Contributors submit a self-contained adapter directory and CI executes the benchmark on dedicated cloud hardware.

Plugin Submission (leaderboard/<system>/)
A database developer submits a pull request adding leaderboard/<system>/ with system.json, executable lifecycle hooks (install, start, check, stop), and connector.py exporting CONNECTOR. See the Database Developer Guide for the full contract.
Dedicated Ephemeral VM per System
For self-hosted engines ("hosted": "no"), CI provisions one dedicated ephemeral cloud VM per database system in parallel (standard reference tier, such as 16 vCPUs, 32 GiB RAM, NVMe SSD). Each engine receives 100% of its VM's CPU, memory, and disk I/O with zero noisy-neighbor interference or leftover page cache.
Managed Cloud Services
For hosted services ("hosted": "yes"), the runner executes from a cloud client VM pinned to the same region, requires a client location flag, and records the measured SQL round-trip latency (rtt_ms) alongside the service region.
Unified Board & Hardware Badges
All systems render in one unified ranking table per suite. Every row displays a Hosting badge (Self-hosted vs. Managed service) and a Hardware / Spec badge (such as 16 CPUs · 32 GiB or cloud region), paired with top-bar Hosting and Machine filters.
Publication Manifest (publish.json)
python -m leaderboard.site (default prod phase) publishes only records explicitly listed in leaderboard/publish.json that pass full validation (clean git commit, matching suite/dataset SHA-256, full macro preset, and verified database cleanup). The production output in leaderboard/.site/prod/ omits run.html, README.md, architecture.html, and all mock or quick runs.

4. Official Cloud (prod) vs. Local Dev (local)

Both phases execute the exact same runner, validator, and UI scripts; the build phase controls only record selection and developer affordances.

Dimension Official Cloud Leaderboard (prod) Local Developer Mode (local)
Build Command python -m leaderboard.site (default is prod) python -m leaderboard.site --phase local
Output Directory leaderboard/.site/prod/ leaderboard/.site/local/
Execution Hardware 1 Self-Hosted DB = 1 Dedicated Cloud VM in CI. Developer workstation running 1 database at a time under run.lock.
Server Lifecycle Fresh VM executes leaderboard/<system>/{install,start,check,stop} and terminates. Local runner executes leaderboard/<system>/{install,start,check,stop} with active.json crash recovery.
Record Selection Allowlisted in leaderboard/publish.json; requires clean git tree and full macro preset. All validated local runs in results/ and macro/ (including mini preset) plus leaderboard.mock rows.
Developer Tools Read-only static bundle (no wizard, no /api/run, no developer docs). Includes run.html wizard, architecture.html, README.md, and loopback POST /api/run.
