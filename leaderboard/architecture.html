Benchmark & Submission Architecture

How BranchBench ranks branching databases fairly across self-hosted engines and managed cloud services.

1. What We Measure

BranchBench evaluates databases that support Git-like branching, copy-on-write forks, and point-in-time recovery for AI agent workloads.

Macrobench (Agent workflows)
Six end-to-end agent scenarios (S1 RL environment, S2 Context management, S3 Multi-agent, S4 Dev agent, S5 Ops agent, S6 Data agent) exercising nine branching verbs (branch, commit, diff, log, merge, rebase, revert, reset, delete) alongside concurrent SQL reads and writes.
Microbench (Operations)
Isolated primitive latencies on a seeded CH-benCHmark dataset: Time to first query on a new branch, branch creation & connection chains, point/range reads & writes, and initial data load.

2. Hardware Fairness & Isolation

Databases range from single-binary engines (Dolt, Postgres) to distributed clusters (TiDB, MatrixOne, SeekDB) and cloud serverless services (Neon). BranchBench uses a unified table with explicit hardware attribution:

Unified Table + Row Badges
All systems appear in one unified table per suite. Every row displays a Hosting badge (Self-hosted vs. Managed service) and a Hardware / Spec badge (e.g. 16 CPUs · 32 GiB or cloud region aws-us-east-1).
Standard Reference VM Default
Official self-hosted runs default to one standard cloud VM tier (e.g. AWS c6i.4xlarge: 16 vCPUs, 32 GiB RAM, NVMe SSD). If a distributed engine requires a larger VM tier to boot, its badge and the top-bar Machine filter make the hardware difference visible immediately.

3. How Database Developers Submit a System (1 Self-Hosted DB = 1 VM)

Contributors submit code and lifecycle hooks — never timing JSON files from their own laptops.

Step 1 — Self-Contained Plugin Folder (leaderboard/<system>/)
Add a self-contained directory inside leaderboard/<system>/ without modifying core files outside leaderboard/: system.json (metadata, hosting mode, capability tags), connector.py (exporting CONNECTOR subclassing leaderboard.connector.Connector), and executable lifecycle scripts (install, start, check, stop) for self-hosted servers.
Step 2 — Ephemeral VM per System
CI launches 1 dedicated ephemeral cloud VM per self-hosted system in parallel. Each database gets 100% of its VM's CPU, RAM, and disk I/O with zero noisy-neighbor interference or leftover OS page cache from other engines.
Step 3 — Validate & Publish
Each VM executes the system's lifecycle hooks via python -m leaderboard.run <system> --machine <vm> and python -m leaderboard.run_macro <system> --preset full --machine <vm>, verifies all correctness invariants and cleanup checks, and records the validated result path in leaderboard/publish.json.

4. Official Leaderboard (prod) vs. Local Dev Architecture (local)

The same codebase powers both the public leaderboard and local developer benchmarking, separated by build phase:

Dimension Official Public Leaderboard (--phase prod) Local Developer Mode (--phase local)
Primary Goal Universal, apples-to-apples public comparison across database systems. Fast connector development, local hardware testing, and debugging via run.html.
Execution Environment 1 System = 1 Ephemeral Cloud VM (dedicated CPU/RAM/NVMe per database in CI). Developer's own workstation/laptop (e.g. apple-m5-32gb) running 1 database at a time.
Database Lifecycle Fresh VM runs leaderboard/<system>/{install,start,check,stop} from scratch, then destroys the VM. leaderboard.run invokes leaderboard/<system>/{install,start,check,stop} locally around the benchmark run.
Data Source Gate Strictly allowlisted by leaderboard/publish.json; requires clean git commit & full preset. Auto-discovers all validated local runs in leaderboard/*/results/ and leaderboard/*/macro/.
Interactive Runner UI Static read-only site (run.html and /api/run omitted). Includes run.html wizard + live leaderboard.serve HTTP runner (/api/run, live logs).
