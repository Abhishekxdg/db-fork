Technical Architecture: Entrypoints to Leaderboard Generation

How BranchBench orchestrates database benchmarks across local workstations (local), collapsible personal AWS staging stacks (alpha), and official AWS batch workers (prod), enforcing single-run hardware isolation, crash-safe teardown journals, and fail-closed static site assembly.

3. Architectural Boundary & Benchmark Suites

The leaderboard/ package is a self-contained harness and static site builder layered over dblib/, microbench/, and macrobench/ without modifying upstream files.

Open-Closed Boundary
All runner orchestration, system lifecycle hooks, connector shims, AWS deployment scripts, and UI assets live strictly inside leaderboard/. Automated boundary tests (test_no_files_outside_leaderboard_differ_from_main_merge_base) verify that zero files outside leaderboard/ differ from origin/main.
Macrobench (Agent workflows)
Six end-to-end stateful AI agent scenarios (rl_env, context_mgmt, multi_agent, dev_agent, ops_agent, data_agent) exercising nine Git-like branching verbs (branch, commit, diff, log, merge, rebase, revert, reset, delete) alongside concurrent SQL reads and writes. Ranked by one workflow's completion time at a time among verified attempts.
Microbench (Operations)
Eight isolated operations (time_to_first_query, branch_create, branch_connect, read, range_read, insert, update, range_update) plus initial load_time and provision_time on a deterministic CH-benCHmark seed (leaderboard/suite.json). Ranked by shifted geometric mean of ratios against the fastest comparable system.

4. Local Developer Setup (LEADERBOARD_PHASE=local)

Designed for database developers building and verifying a connector on their own workstation before opening a pull request. Displays a compact mint LOCAL badge in the top brand header.

CLI & HTTP Runner
python -m leaderboard.run <system> --machine <id> runs the microbench suite; python -m leaderboard.run_macro <system> --preset {mini|full} --machine <id> runs all six agent workflows in isolated subprocesses. python -m leaderboard.serve --phase local serves the site on port 8765 and exposes POST /api/run on loopback (127.0.0.1 / ::1), rejecting non-loopback or cross-origin requests with HTTP 403.
Single-Run Lock (run.lock)
Both runners acquire an exclusive non-blocking file lock at leaderboard/.runs/run.lock. Only one database benchmark can execute at a time on a machine so engines never contend for CPU cores, memory bandwidth, disk I/O, or local ports.
Crash Recovery Journals
Before starting a server or creating a benchmark database, the microbench runner writes leaderboard/.runs/<system>.journal.json and the macrobench runner writes leaderboard/.runs/<system>.active.json. If a process is killed by SIGKILL or power loss, the next run replays any leftover journal to delete orphaned databases and run the system's stop hook before starting.
Local Site Assembly
python -m leaderboard.site --phase local scans leaderboard/*/results/ and leaderboard/*/macro/, validates every record against leaderboard/suite.json, pairs local runs with leaderboard.mock reference rows, and atomically swaps a staging directory into leaderboard/.site/local/.

5. Personal AWS Alpha Setup (LEADERBOARD_PHASE=alpha · Collapsible)

Designed for staging real benchmarks on cloud NVMe hardware in your own AWS account and collapsing every resource back to $0.00/hr immediately after testing. Displays a compact amber ALPHA badge in the top brand header.

One-Command Lifecycle
./leaderboard/aws_alpha.sh {up,run,deploy-site,status,collapse} (backed by python -m leaderboard.aws_alpha) tags every provisioned AWS resource with Project=BranchBenchLeaderboard, Phase=alpha, and Stack=<stack>, recording state in leaderboard/.runs/aws_alpha_state.json.
Provision & Execute
up provisions a Spot i4i.2xlarge Ubuntu 24.04 runner with local NVMe formatted as XFS (reflink=1 for PostgreSQL FILE_COPY cloning), a Caller-IP-only (/32) SSH Security Group, and a private S3 bucket (BlockPublicAcls=true) protected by bucket-tag ownership checks. run syncs tracked repository sources over SSH, passes hosted DB credentials via encrypted SSH stdin, invokes leaderboard/aws_worker.sh, pulls results, and runs python -m leaderboard.site --phase alpha.
Real Runs Without Mock Rows
python -m leaderboard.site --phase alpha publishes all validated microbench and macrobench records found on disk (both mini and full presets) without requiring publish.json and without injecting leaderboard.mock rows or the macOS-only run.html launcher.
Complete Collapse to Zero Cost
./leaderboard/aws_alpha.sh collapse discovers resources by both local state and AWS tags, terminates the EC2 runner, deletes any leftover EBS volumes, security groups, and key pairs, verifies ownership tags before emptying and deleting the S3 bucket (unless --keep-bucket is passed), and removes local state and PEM files once every deletion succeeds.

6. Official Cloud Production Setup (LEADERBOARD_PHASE=prod)

Official rankings never ingest timing JSON files from developer laptops. Contributors submit a self-contained adapter directory and the official runner executes on dedicated cloud NVMe hardware. The production UI removes the phase badge completely.

Plugin Submission (leaderboard/<system>/)
A database developer submits a pull request adding leaderboard/<system>/ with system.json, executable lifecycle hooks (install, start, check, stop), and connector.py exporting CONNECTOR. See the Database Developer Guide for the full contract.
Economic Single-VM Sequential Batch (aws_worker.sh)
In official AWS production, ./leaderboard/aws_worker.sh --machine <id> --preset full runs all database adapters sequentially on one shared bare-NVMe instance (such as i4i.2xlarge) under batch.lock and run.lock. Before and between engines, the worker checks that conflicting systemd units are inactive, runs the adapter's stop hook, calls os.sync(), and verifies host cleanliness (no live server PID, no listening port, and no leftover recovery journal) so every database gets 100% of the machine with identical hardware provenance.
Managed Cloud Services
For hosted services ("hosted": "yes"), the runner executes from the cloud worker pinned to the target region, verifies credentials via preflight() before creating any project, requires --client-location, and records measured SQL round-trip latency (rtt_ms) alongside the service region.
Publication Manifest (publish.json)
python -m leaderboard.site (default prod phase) publishes only records explicitly listed in leaderboard/publish.json that pass full validation (clean git commit, matching suite/dataset SHA-256, homogeneous comparison group, full macro preset, and verified database cleanup). The production output in leaderboard/.site/prod/ omits run.html, README.md, architecture.html, the phase badge, and all mock or quick runs.
